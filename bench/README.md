# Benchmarks

How BertBrowser's speed is measured, kept, and defended. The tool is `tools/BertBrowser.Bench`; the
evidence is `docs/performance.md`, generated from the baselines in this folder.

## Layout

| Path | What |
|---|---|
| `bench/baselines/<machine-key>.json` | One committed baseline per machine, all tiers merged. Compare runs against the one matching the current machine. |
| `bench/baselines/<machine-key>.real.json` | The same machine measured against its own real index and folders (`--real`). Never compared with a synthetic file. |
| `bench/baselines/ci-windows-latest.json` | The GitHub runner's baseline. CI gates allocations against it. |
| `bench/real.local.json` | Your real-data config. Gitignored. |
| `bench-results/` | Where runs land. Gitignored. |
| `docs/performance.md` | Generated by `report`. Never edit by hand. |
| `%LOCALAPPDATA%\bertbrowser-bench\` | The cached synthetic corpus, BenchmarkDotNet artifacts, real-DB backups. Safe to delete. |

## Three tiers, one schema

| Tier | Measures | How | Unit |
|---|---|---|---|
| A | Core code paths: search, index writes, planners, hashing, preview readers… | BenchmarkDotNet, in `tools/BertBrowser.Bench/Benchmarks` | ns, bytes allocated |
| B | Whole UI scenarios: open a 10k folder, flat view, tiles, search, transfer, preview | The offscreen harness, `tools/ui/bench-*.bbs`, each scenario K times in a fresh process | ms, process memory |
| C | Startup of the real `BertBrowser.exe` to first listing | N launches against a scratch data dir, marks written by the app | ms |

A Tier B script is an ordinary harness script with three extra verbs: `time <name> <verb>[; <verb>…]`
wraps any verb (or chain) under a stopwatch, `mem <name>` reads the process back after a full
collection, and `settle-thumbnails` / `settle-preview` wait for the two things `Settle` deliberately
does not. A `#! files=10000 dirs=50` line carries the fixture size into the result. `BertBrowser.Bench
ui` runs each script K times as separate processes and takes the median.

Tier C refuses while a real BertBrowser is running: the single-instance claim is per user, so the
launch would be a "second" copy and measure a different path. `--allow-running` measures it anyway and
records `instance=second`; do not commit that as a baseline.

Every tier writes `Core/Benchmarking/BenchResultSet` JSON. Only the Bench exe writes it; the harness and
the app emit raw samples it aggregates.

## The loop

```powershell
dotnet build bertbrowser.sln -c Release
$bench = "tools\BertBrowser.Bench\bin\Release\net10.0\BertBrowser.Bench.exe"

& $bench run --filter *FsIndex*               # measure what you are working on (BDN glob over Class.Method)
# ...change code, rebuild...
& $bench run --filter *FsIndex* --out bench-results\after.json
& $bench compare --baseline bench\baselines\<your-key>.json --current bench-results\after.json
```

`compare` exits 1 on a regression: a median more than 15% slower than the baseline (and past a small
absolute noise floor), or more bytes allocated than the benchmark's tolerance allows. Exit 2 means a
benchmark errored.

### Recording a baseline

```powershell
& $bench run                      # Tier A, default job — long; this is the number that gets committed
& $bench ui --repeat 5            # Tier B
& $bench startup --launches 10    # Tier C — a window appears offscreen for a second per launch
& $bench baseline --from bench-results\current.json --from bench-results\ui.json --from bench-results\startup.json
& $bench report
git add bench\baselines docs\performance.md
```

A new machine has no baseline; the first `baseline` creates it. **Re-record deliberately.** When a
change is slower on purpose — a correctness fix, a feature that costs something — re-record in the same
commit and say why in the message. The baseline is a statement, not a log.

To re-record one tier, pass the existing baseline first so the others survive:
`baseline --from bench\baselines\<key>.json --from bench-results\ui.json`.

### CI

The `bench` job in `unstable.yml` runs Tier A with the short job and `compare --ci`, which **gates
allocations only** — wall-clock on a shared runner is noise and is reported, not judged. The job
summary carries the table; the results are an artifact. On the first run (no baseline committed) it
writes `candidate-baseline.json` into the artifact and passes; commit that as
`bench/baselines/ci-windows-latest.json`. Accepting an allocation change is the same move.

The job runs beside the build, not before it: a red benchmark never withholds an unstable build.

## Allocation tolerance

Pure code allocates exactly the same bytes every run, and one extra object is the regression the CI
gate exists for. Code over SQLite, the thread pool or disk does not have that property. Those
benchmark classes carry `[AllocationTolerance(2)]` (five for the end-to-end disk scans) and the
tolerance travels in the result. Do not loosen a pure benchmark to make a run pass.

## Real data

`--real` runs the read-only subset against your actual index and folders. It never opens the live
database: it takes a SQLite backup into `%LOCALAPPDATA%\bertbrowser-bench\real\` once a day and reads
that. `bench/real.local.json`:

```json
{
  "dbPath": "C:\\Users\\you\\.bertbrowser\\bertbrowser.db",
  "searchRoot": "C:\\Source",
  "listingFolder": "C:\\Windows\\System32",
  "treeFolder": "C:\\Source",
  "textFolder": "C:\\Source",
  "mediaFolder": "D:\\Photos"
}
```

Results go to `bench-results/current.real.json` and baselines to `<key>.real.json`.

## Noise

- **Compare like with like.** The default toolchain (a child process per benchmark class) and the
  in-process one do not report the same allocations for code over SQLite or the hashing APIs — MD5 over
  64 MB reads 333 B one way and 1.6 KB the other — and the short job's times are three samples. The
  job and toolchain are recorded in every results file; `compare` says so above the table when they
  differ. The committed machine baselines are default job, default toolchain; the CI baseline is short
  job, in-process, recorded by CI itself.
- Close what you can; plug in; use the High performance power plan (the plan is recorded).
- The index helper tails the USN journal into your database the whole time. It is recorded as
  `indexerRunning`; stop it if you want quiet disks, but a baseline recorded with it running is still a
  fair baseline for a run with it running.
- Tier B renders under WPF's software rasteriser, parked offscreen. It is a regression signal for
  view-model and layout work, not what a user's GPU sees.
- Tier C skips the post-window side effects (index attach, change-log policy, update check) — the
  change-log push would wipe your real change log from a scratch data dir — so it measures "to first
  listing", not "to idle".
- Medians, not means. A single slow sample is the machine.
